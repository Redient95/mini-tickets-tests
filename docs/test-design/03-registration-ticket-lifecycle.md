\## Область и границы модели



Сквозной процесс: регистрация → вход → создание заявки → работа с новой заявкой

→ перевод оператором в active → перевод в closed → повторное открытие.



В модель входят требования: AUTH-01, AUTH-02, AUTH-03,

TICKET-01, TICKET-02, TICKET-03, TICKET-04, COMMENT-01.



Вне модели: восстановление пароля, удаление пользователя, админские операции,

оплата, e-mail рассылки.

\## Сквозной бизнес-сценарий



1\. Регистрация нового пользователя.

2\. Вход, получение Bearer-токена.

3\. Создание заявки.

4\. Найти её в списке и карточке.

5\. Оператор переводит `new → active`.

6\. Оператор переводит `active → closed`.

7\. Подтверждение итогового состояния.

\## Применение принципов тестирования



| Принцип | Как влияет на модель |

|---|---|

| Тестирование показывает наличие дефектов | Один прогон подтверждает конкретное наблюдение, а не отсутствие всех дефектов |

| Исчерпывающее тестирование недостижимо | Сокращаем комбинации Pairwise и классами |

| Раннее тестирование | Противоречия в требованиях фиксируем до запуска |

| Кластеризация дефектов | Максимум внимания авторизации, границам, переходам |

| Парадокс пестицида | Обновляем данные и комбинации после изменений |

| Тестирование зависит от контекста | Учитываем учебное веб-приложение, REST, PostgreSQL, три роли |

| Заблуждение об отсутствии ошибок | 200 не значит «правильно» — сверяем с бизнес-правилом |

\## Классификация наборов



\*\*Smoke:\*\* зарегистрировать → войти → создать заявку → оператор `new→active→closed` → проверить.



\*\*Sanity-контексты:\*\*

\- после изменения нормализации email — границы email;

\- после изменения валидации заголовка — границы 2/3/4, 79/80/81;

\- после изменения матрицы переходов — все 9 клеток;

\- после изменения проверки роли оператора — 403/200 для оператора.



\*\*Regression:\*\* основной поток + альтернативы + ошибки валидации + авторизация +

владение + все состояния + инварианты.
