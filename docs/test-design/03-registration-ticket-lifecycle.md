\## Область и границы модели



Сценарий: регистрация → вход → создание заявки → работа с новой заявкой → перевод оператором в active → перевод в closed → повторное открытие.



Роли: `user` (автор), `other\_user` (другой пользователь), `operator`.



\## Пользователи, данные и предусловия



| Участник | Роль | Назначение |

|---|---|---|

| Новый пользователь | user | Регистрация, вход, создание заявки |

| Другой пользователь | user | Проверка границы видимости |

| Оператор | operator | Изменение статуса |



Тестовые данные:



| Имя | Значение |

|---|---|

| `email\_valid` | уникальный корректный email |

| `password\_valid` | пароль 8–64 символов |

| `title\_valid` | заголовок 3–80 символов |

| `operator\_token` | токен оператора |

| `owner\_token` | токен автора |

| `other\_user\_token` | токен другого пользователя |



\## Сквозной бизнес-сценарий



1\. Регистрация нового пользователя.

2\. Вход и получение Bearer-токена.

3\. Создание заявки.

4\. Просмотр заявки автором.

5\. Оператор переводит заявку: new → active → closed.

6\. Оператор повторно открывает: closed → active.

\## Применение принципов тестирования



| Принцип | Пример |

|---|---|

| Тестирование показывает наличие дефектов | Проверка email подтверждает одно поведение, не всю систему |

| Исчерпывающее тестирование недостижимо | Pairwise сокращает комбинации |

| Раннее тестирование | Вопросы к требованиям до запуска |

| Кластеризация дефектов | Основное внимание — авторизации и переходам |

| Парадокс пестицида | После изменений обновляем данные |

| Зависимость от контекста | Роли, REST, PostgreSQL |

| Заблуждение об отсутствии ошибок | 200 не значит «всё правильно» |
